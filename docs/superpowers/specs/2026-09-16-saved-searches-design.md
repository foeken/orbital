# Saved searches replace the view presets (2026-09-16)

Display, create, update and save Tana saved searches (`tana:search:<ulid>`) in the companion, and retire the
built-in view presets in favour of searches the user owns.

## 1. Why

The six views are a fixed preset system: `VIEW_PRESETS` in `sdk/query.js`, `VIEWS` in `main/state.js`, one row
cache section per view id. Tana already has the same concept as a first-class, portable, shareable document. Two
mechanisms for one idea, and the user's own searches are invisible in the companion.

The trigger: a saved search pasted into the app showed up nowhere. Root cause was a vocabulary gap, fixed in
TASKS.md #246 — saved searches now *list*. This spec is the rest: opening one, creating one, editing one.

## 2. What was verified, and how

Schema reverse-engineered from Tana's own bundle (`home.tana.inc/assets/shared-*.js`), the route AGENTS.md already
sanctions for descriptors, then **checked against a real document** (the user's "My Tasks"):

```js
xfe = Fc.schema({ data: Fc.map(Lc({})), query: mfe, queryMeta: _fe, view: bfe })
```

- `query` is a **root container, not a key in `data`**. This is why `readNode` (`{id, ...data.toJSON()}`) shows a
  saved search as a bare title: its query is in a container we never read.
- `query` keys, **from the bundle schema** (`pfe`): `textQuery, types, entityTypeUris, ownerUris, createdBy,
  createdByViewer, assignedTo, assignedToViewer, unassigned, participantUris, visibility, stateTypes,
  workflowStates[{workflowUri, workflowStateId}], eventTime{preset, min, max}, attributes{…}`.
  The real document confirmed ten of these: `types, entityTypeUris, ownerUris, createdBy, assignedTo,
  assignedToViewer, participantUris, stateTypes, workflowStates, attributes`. The other five — `textQuery,
  createdByViewer, unassigned, visibility, eventTime` — are **schema-only, not yet seen in a real document**.
  They are consistent with optional keys being omitted rather than written empty, but that is inference.
- `queryMeta` = `{ naturalLanguageQuery? }`; `view` = `{ groupBy?, sortBy?, display: record<{shown, order}> }`.
- Optional keys are **absent**, not empty — the real document has no `queryMeta`, `textQuery`, `groupBy` or
  `sortBy`. Writers must omit rather than write empty values.
- **`assignedToViewer: true`** in the real document: "me" is viewer-relative and portable. There is **no**
  participant equivalent (`participantsViewer` has zero hits), so "events I'm in" must name a URI.

Vocabularies (from the bundle, not guessed):

| thing | values |
|---|---|
| `view.groupBy` | `type` \| `status` \| `assignee` \| a type's field URI — **no `updated`** |
| `view.sortBy` | `startTime` (events only), `updated`, `created`, `title`; `-field` = descending |
| `eventTime.preset` | `recent` \| `upcoming` \| `today` \| `past` |
| `visibility` | `private` \| `shared` \| `restricted` \| `open` \| `link` |

Tana's own write API: `createSearchDoc({title, titleAutoGenerated, naturalLanguageQuery, query, view, acl})`;
mutations `setQuerySpec`, `setViewSpec`, `setNaturalLanguageQuery`, `refreshAutoGeneratedTitle`. Types carry
`searches: [{uri, label?}]` via `attachSearch`/`detachSearch` — **out of scope here**.

## 3. Model

A stored search replaces a view preset. The Library stays the general browsing surface. Cmd+K gains a `Searches`
group; sidebar pinning comes free because pins take any URI (`docs/PINNING.md`).

## 4. Read path

Extend the kind switch at `main.js:93`, mirroring `spaceChildren`:

```js
isSearch(id) ? searchChildren(id) : isSpace(id) ? spaceChildren(id) : op(id, …)
```

`searchChildren(id)` reads the document's `query` container, translates it to `listNodes` params, and maps results
through the existing `toNode(graphRow(n))` pipeline with `rememberNodeHue` + `resolveTypes` — exactly as
`spaceChildren` does. Zoom, breadcrumbs, the rail, row rendering, keyboard navigation and live updates then work
with no new UI machinery.

Translation to `ListNodesRequest` (all fields confirmed present on the request):

| stored | request |
|---|---|
| `textQuery`, `types`, `entityTypeUris`, `stateTypes`, `assignedTo`, `createdBy`, `unassigned` | `textQuery`, `nodeTypes`, `entityTypes`, `stateTypes`, `assignedTo`, `createdBy`, `unassigned` |
| `ownerUris` | `ownerIds` |
| `participantUris` | `hasParticipantUris` |
| `eventTime{min,max}` | `eventStartTimeMin`/`Max` |
| `assignedToViewer` / `createdByViewer` | resolved to the signed-in user's URI |
| `attributes` | `attributeFilters` — Tana-uri `refs`, `date` → `dateRanges`, `textMatches` modes → `MODE_*`, non-empty `numberRanges` (Tana's `C$`, verified 2026-09-22) |
| `workflowStates` | `stateSelectors`: the plain states plus `{ type: 'open', workflowUri, workflowStateId }` per workflow state |
| `visibility` | `private` → restricted + only me; `shared` → me among the participants; `restricted`; `open` → `restricted: false`; `link` → `linkShared` |

`eventTime` applies only to a search for events alone, and its preset is resolved on local days as Tana does:
`recent` runs to the end of tomorrow, `upcoming` from now (soonest first), `past` until now, `today` is today.

## 5. Cache

`db.js` keys rows by `(section, document)` with `section` an opaque string — chosen because views overlap. It
becomes the search URI with no schema change; `replaceSection`/`list()` are untouched. Boot-from-cache and refresh
behave as they do today.

## 6. Write path

- `initDocument` gains a `search` kind: `data.type='search'`, `createdAt`, `title`, plus the `query`, `queryMeta`
  and `view` root containers. `Document.transact(fn)` passes the raw `loro`, so `loro.getMap('query')` works —
  **no change to `sdk/document.js`**.
- Save: translate the active view filter to a query, create the document, optionally pin it.
- Update: rewrite the `query` container (Tana's `setQuerySpec` replaces every key); `view` likewise.
- Only write keys that have values — optional keys are absent in real documents.

**ACL is not guessed.** `sdk/access.js` (`KINDS`, `ORGANIZED`) is untouched, per the standing rule against
inventing ACL or move semantics. A search is created with the same participants/`restricted` shape our other
`initDocument` kinds use. Sharing and moving a search are out of scope.

## 7. Kept client-side, deliberately

Presentation state keyed by search URI, not written into the document:

- **Group by `updated`** — not in Tana's group vocabulary. Writing it would put a value Tana cannot render into a
  shared document.
- **Sort `default`** ("the view's own order") — no equivalent.

## 8. Removals

- **The MCP chats toggle** (decided 2026-09-16). `chatInvocationIntents` exists on `ListNodesRequest` and in
  liveQuery params but **not** in the saved-search query schema, so it can never round-trip as a stored filter.
  Rather than keep it as a local preference it is dropped outright: `mcp` leaves the filter vocabulary
  (`FILTER_KEYS`, `validViewFilter`, `VIEW_PRESETS.chats`), the pill goes, and the post-query filtering on the
  node goes with it. Chats then list unfiltered, MCP ones included. Cheapest done early, before anything
  translates the filter vocabulary.
- **People view.** Verified safe: member data comes from `main/rows.js`'s own `listNodes({nodeTypes:
  ['user-profile']})` behind `tana.members()`, which the assignee picker uses. Removing the view does not affect
  assignee names or pickers. Touches ~15 sites plus tests; most of the 65 `people` matches are the unrelated
  *sharing* sense.
- **The remaining presets**, once equivalent searches exist — phased (§9), never in one step.

## 9. Phasing

1. **Read.** `searchChildren`, opening a search, Cmd+K `Searches` group. No writes, no removals. Fully testable
   offline and in the mock.
2. **Save.** "Save these filters as a search" + create. First writes; scratch-document verification (§11).
3. **Edit.** Rewrite `query`/`view` from the pills; local prefs for the §7 items.
4. **Retire.** Remove People, then the presets, once searches cover them.

## 10. Risks and open questions

- **RESOLVED 2026-09-17: the `data` map on create.** A raw container dump of the user's real "My Tasks"
  search settled it. Root containers are `data`, `query`, `view`, plus an empty `content` and an empty
  `linkSharing`; `queryMeta` is **absent**, confirming optional containers are omitted rather than
  written empty. The `data` map holds exactly: `type: "search"`, `createdAt`, `title`,
  `restricted: true`, and `participants: { <user-profile uri>: { type: "user", role: "admin" } }`.
  **There is no `ownerUri`** — consistent with a Library-level search having no owner (AGENTS.md: no
  owners = "Library"), so `Th.create`'s `ownerUri` write is conditional in practice.
  Two consequences: (1) **rename needs only the kind gate** — `participants[user].role` is `admin`, so
  `editable()` returns `true` once `search` joins its kind list, rather than the `null` (unknown) I
  feared; (2) **create maps almost exactly onto our existing `initDocument`**, which already writes
  `type`/`title`/`createdAt`/`restricted`/`participants`-as-admin. The deltas are narrow: add the
  `query` and `view` root containers, and **skip `sharedPinDates`**, which `initDocument` creates for
  doc/task/meeting but a real search does not carry.
- *(superseded)* **OPEN: the `data` map on create.** The real-document dump showed `uri`/`title`/`createdAt` and the `query` and
  `view` containers, but not the rest of `data`. `data.type === 'search'`, `ownerUri` and the acl shape are
  therefore **unverified**, and they are exactly what create writes. Must be confirmed (a raw container dump)
  before phase 2 ships.
- Writing a malformed document into a real graph is the main hazard; mitigated by scratch documents.
- Retiring presets before searches exist would leave the app with no navigation — hence the phasing.
- Tana may change this schema with any deploy; it is undocumented. Same standing risk as the rest of the protocol.

## 11. Verification

- Offline: `npm run check` — `sdk-check` for the query translation both ways; renderer checks for the palette
  group and row rendering.
- Mock: opening a search and seeing rows; "save as search" producing a document.
- Real data: **writes only against a scratch search document** (create, edit, delete) via an escalated run, never
  against the user's own searches. Reads may use "My Tasks".

## 12. Out of scope

Attaching searches to types (`attachSearch`/`detachSearch`), `naturalLanguageQuery` authoring, sharing/moving a
search, field filters (`attributes`) authoring in the UI, and Tana's `display` column configuration.
