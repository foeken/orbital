# Decisions this informs

- Keep one Android `WebView` as Orbital's Tana session and JS runtime, loaded only at `https://home.tana.inc`. Register an origin-restricted `WebViewCompat.addWebMessageListener`, bridge its injected object to the `window.webkit.messageHandlers.orbital.postMessage(...)` shape used by iOS, and send the existing `ready` and `changed` events. Add the engine before page scripts with `addDocumentStartJavaScript` when supported, and feature-check each AndroidX WebKit API. ([WebView bridge guide](https://developer.android.com/develop/ui/views/layout/webapps/native-api-access-jsbridge), [WebViewCompat](https://developer.android.com/reference/androidx/webkit/WebViewCompat), [iOS bridge](../ios/Orbital/Engine.swift), [engine](../ios/engine/index.js))
- Do not run Google OAuth inside that WebView or try to make it look like Safari. Google identifies this as `disallowed_useragent` and recommends native sign-in with Credential Manager on Android; use the system browser for general OAuth redirects. ([Google OAuth native-app errors](https://developers.google.com/identity/protocols/oauth2/native-app), [Google Sign in best practices](https://developers.google.com/identity/siwg/best-practices), [Android Credential Manager](https://developer.android.com/identity/credential-manager))
- The current Chromium Blink synchronous main-thread WebAssembly size guard is **8,388,608 bytes (8 MiB)**. The locked `loro-crdt@1.16.1` base64 entry contains a **3,240,077-byte** decoded module and synchronously constructs its `WebAssembly.Module` and instance, so its present WASM payload fits with more than 5 MB of headroom. This verifies the module-size question; validate the 4.64 MB JavaScript injection itself and the oldest supported Android System WebView on-device. ([current Chromium source](https://chromium.googlesource.com/chromium/src/third_party/%2B/master/blink/renderer/bindings/core/v8/v8_initializer.cc), [locked package](../package-lock.json), [installed base64 entry](../node_modules/loro-crdt/base64/index.js), [Orbital engine build](../ios/engine/build.js))
- Use **AGP 9.3.1 + Gradle 9.6.0 + Kotlin 2.4.20** for the first KMP build: Kotlin's published compatibility table includes AGP only through 9.3.1 for Kotlin 2.4.20, even though AGP 9.4.1 is the latest stable AGP returned by the Android CLI lookup. AGP 9 app modules use built-in Kotlin instead of `org.jetbrains.kotlin.android`; the KMP shared module still uses `org.jetbrains.kotlin.multiplatform` and `com.android.kotlin.multiplatform.library`. ([Kotlin compatibility](https://kotlinlang.org/docs/gradle-configure-project.html), [AGP releases](https://developer.android.com/build/releases/about-agp), [built-in Kotlin](https://developer.android.com/build/migrate-to-built-in-kotlin), [KMP plugin](https://developer.android.com/kotlin/multiplatform/plugin))
- For the iPhone interaction model, start with a Material 3 `DismissibleNavigationDrawer` on phones, `PullToRefreshBox`, accessible `combinedClickable` menus, Navigation 3 predictive back, and adaptive list/detail layouts. Use edge-to-edge plus IME insets for the composer. ([drawers](https://developer.android.com/develop/ui/compose/components/drawer), [pull to refresh](https://developer.android.com/develop/ui/compose/components/pull-to-refresh), [tap and press](https://developer.android.com/develop/ui/compose/touch-input/pointer-input/tap-and-press), [Navigation 3](https://developer.android.com/guide/navigation/navigation-3), [edge-to-edge](https://developer.android.com/develop/ui/compose/system/setup-e2e), [adaptive layouts](https://developer.android.com/develop/adaptive-apps/guides/use-window-size-classes))
- Put fast host tests in KMP's opt-in `androidHostTest` source set, real WebView/system behavior in instrumented `androidDeviceTest`, and cross-app journeys in UI Automator. Prefer Roborazzi for screenshots shared with the KMP module; Android's Preview Screenshot Testing plugin is still experimental and does not support KMP. ([KMP test source sets](https://developer.android.com/kotlin/multiplatform/plugin), [Compose testing](https://developer.android.com/develop/ui/compose/testing), [Roborazzi](https://github.com/takahirom/roborazzi), [Compose screenshot testing](https://developer.android.com/studio/preview/compose-screenshot-testing))

## WebView bridge and lifetime

`WebViewCompat.addWebMessageListener` injects a named JavaScript object only on the configured origin rules. Its native callback receives the message, source origin, main-frame flag, and a `JavaScriptReplyProxy`; use the exact `https://home.tana.inc` rule, reject non-main-frame messages, validate the reported source origin, and keep the bridge's callable surface small. `WebViewFeature.isFeatureSupported` should guard `WEB_MESSAGE_LISTENER`, `DOCUMENT_START_SCRIPT`, and any other AndroidX WebKit feature before use. ([WebView bridge guide](https://developer.android.com/develop/ui/views/layout/webapps/native-api-access-jsbridge), [WebViewCompat](https://developer.android.com/reference/androidx/webkit/WebViewCompat), [WebViewFeature](https://developer.android.com/reference/androidx/webkit/WebViewFeature))

Register `addDocumentStartJavaScript` before loading Tana so the engine shim exists before page JavaScript runs. The injected code runs before the DOM is ready and blocks page loading until it finishes, so use it to install a small compatibility shim and start the engine deliberately; do not put unrelated startup work there. `evaluateJavascript` runs asynchronously on the UI thread and returns its evaluated result through a callback after the page is loaded. `onPageFinished` reports navigation completion, not Orbital engine readiness, so use the existing JavaScript `ready` message as the app-level gate. The API does not promise to await a JavaScript `Promise`, so explicitly await work in page JavaScript and post the result through the bridge. Android's API reference publishes no byte-size limit for either script string; it therefore does not certify a 5 MB injection as safe on every provider/device. ([WebViewCompat](https://developer.android.com/reference/androidx/webkit/WebViewCompat), [`evaluateJavascript`](https://developer.android.com/reference/android/webkit/WebView#evaluateJavascript(java.lang.String,android.webkit.ValueCallback)), [`onPageFinished`](https://developer.android.com/reference/android/webkit/WebViewClient#onPageFinished(android.webkit.WebView,java.lang.String)), [Orbital bridge](../ios/engine/index.js))

`CookieManager` owns WebView cookies; `flush()` writes accessible cookies to persistent storage and can perform I/O synchronously. Set third-party-cookie policy on the specific WebView only if a tested Tana flow needs it; Android's documented default is false for apps targeting Lollipop or later. Tana's own session is first-party to `home.tana.inc`. ([CookieManager](https://developer.android.com/reference/android/webkit/CookieManager), [third-party-cookie guidance](https://developer.android.com/reference/android/webkit/CookieManager#setAcceptThirdPartyCookies(android.webkit.WebView,boolean)))

Do not use `WebSettingsCompat.setRequestedWithHeaderOriginAllowList` as an auth or identity signal: AndroidX WebKit 1.15.0 deprecated it because it no longer does anything. Keep the system WebView user agent; changing it to a Safari string does not change Google's embedded-user-agent policy. Google explicitly disallows OAuth requests in an embedded user agent controlled by the app, reports `disallowed_useragent`, and recommends Android Credential Manager for Sign in with Google. For OAuth flows that need browser redirects, use a system browser/Custom Tab and the native-app redirect pattern. ([WebSettingsCompat](https://developer.android.com/reference/androidx/webkit/WebSettingsCompat), [Google policy](https://developers.google.com/identity/protocols/oauth2/policies), [native-app OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [Credential Manager](https://developer.android.com/identity/credential-manager))

Web content debugging is available through `WebView.setWebContentsDebuggingEnabled`; WebView 113+ enables it automatically for debuggable apps, and it allows inspection and modification through ADB, so keep it to debug builds. A WebView uses a separate Chromium renderer and can consume substantial native memory; Android may kill that renderer under pressure. A hidden WebView can remain alive while its owning Activity/process remains alive, but it is not a durable background JavaScript service. Handle `onRenderProcessGone` by discarding and recreating the WebView, restoring the bridge and session as needed; avoid pausing timers if the engine must continue syncing. ([debugging API](https://developer.android.com/reference/android/webkit/WebView#setWebContentsDebuggingEnabled(boolean)), [WebView memory](https://developer.android.com/develop/ui/views/layout/webapps/manage-webview-memory), [renderer termination](https://developer.android.com/develop/ui/views/layout/webapps/managing-webview#handle-termination))

## WebAssembly and Loro

Chromium's current Blink source sets `kWasmWireBytesLimit = 1 << 23`, or **8,388,608 bytes**. The guard rejects synchronous main-thread `WebAssembly.Module` input only when its byte length is greater than that limit, so exactly 8 MiB passes; the synchronous `WebAssembly.Instance` path also has a module-size guard. The same source says the limit was raised from 4 KiB after measuring an 8 MB compile under 200 ms on a Pixel 1. This is a Chromium implementation limit, not a Web standard guarantee, and installed Android System WebView versions can lag Chromium main. ([current Blink source](https://chromium.googlesource.com/chromium/src/third_party/%2B/master/blink/renderer/bindings/core/v8/v8_initializer.cc), [change introducing 8 MB](https://chromium.googlesource.com/chromium/src/%2B/d1a1a8fdd9b28feaf5d3accc0578092444a1083e%5E%21/))

The guard counts decoded WebAssembly bytes, not the total JavaScript bundle. In the locked `loro-crdt@1.16.1`, `base64/index.js` is 4,644,264 bytes; its embedded base64 string is 4,320,104 characters and decodes to **3,240,077 bytes**. The entry calls the loader in synchronous mode, which executes `new WebAssembly.Module(buf)`; Orbital's engine then synchronously constructs the `WebAssembly.Instance` during module evaluation. The size is therefore below the current 8 MiB main-thread guard. ([package lock](../package-lock.json), [installed base64 entry](../node_modules/loro-crdt/base64/index.js), [engine build selector](../ios/engine/build.js), [Chromium guard](https://chromium.googlesource.com/chromium/src/third_party/%2B/master/blink/renderer/bindings/core/v8/v8_initializer.cc))

The iOS engine build selects this `loro-crdt/base64` entry, and Loro's upstream README describes it as the inline-WASM path that avoids top-level await. The installed entry is 4.64 MB before Orbital's other engine code is bundled, so the 5 MB estimate is plausible. The WebView APIs publish no script-string byte limit, however; test the full Android bootstrap on the oldest supported Android System WebView to verify injection/startup time and renderer memory as well as WASM compatibility. ([Loro README](https://github.com/loro-dev/loro/tree/main/crates/loro-wasm), [installed base64 entry](../node_modules/loro-crdt/base64/index.js), [Orbital build selector](../ios/engine/build.js), [WebViewCompat](https://developer.android.com/reference/androidx/webkit/WebViewCompat), [evaluateJavascript](https://developer.android.com/reference/android/webkit/WebView#evaluateJavascript(java.lang.String,android.webkit.ValueCallback)))

If the decoded module exceeds the limit, Chromium's error text recommends asynchronous `WebAssembly.compile`/`WebAssembly.instantiate` or compilation on a worker. That would require adapting the synchronous Loro startup path; the size estimate above does not suggest this is immediately necessary. ([Chromium guard and alternatives](https://chromium.googlesource.com/chromium/src/third_party/%2B/master/blink/renderer/bindings/core/v8/v8_initializer.cc), [Loro browser entry guidance](https://github.com/loro-dev/loro/tree/main/crates/loro-wasm))

## Compose behavior

Material 3's `DismissibleNavigationDrawer` keeps a drawer beside the content and lets the page move with it; `ModalNavigationDrawer` overlays a scrim. The former matches a side-menu-that-pushes-the-page interaction on compact windows, while a permanent drawer or navigation rail is more appropriate when the adaptive window class has room. `PullToRefreshBox` accepts explicit `isRefreshing` and `onRefresh` state for refreshable lists. ([drawer types](https://developer.android.com/develop/ui/compose/components/drawer), [DismissibleNavigationDrawer](https://developer.android.com/reference/kotlin/androidx/compose/material3/DismissibleNavigationDrawer.composable), [adaptive navigation](https://developer.android.com/develop/adaptive-apps/guides/build-adaptive-navigation), [pull to refresh](https://developer.android.com/develop/ui/compose/components/pull-to-refresh))

Use `Modifier.combinedClickable` for tap plus long-press, expose an `onLongClickLabel`, and anchor a `DropdownMenu` to the row; this gives TalkBack a discoverable long-click action in addition to the visual gesture. Use `LocalHapticFeedback` for brief confirmation such as a long-press or successful action, rather than vibrating on every row interaction. ([tap and press](https://developer.android.com/develop/ui/compose/touch-input/pointer-input/tap-and-press), [Compose haptic feedback](https://developer.android.com/reference/kotlin/androidx/compose/ui/hapticfeedback/LocalHapticFeedback), [Compose semantics](https://developer.android.com/develop/ui/compose/accessibility/semantics))

Use Navigation 3's built-in back support for the app stack; for a custom stack, use the Navigation Event `NavigationBackHandler` integration so predictive-back progress and cancellation are available. A local compact list/detail pane can use `BackHandler` to clear the selected detail and return to the list without changing app-level navigation. Enable edge-to-edge in the Activity, set `adjustResize` so the Activity receives IME insets, and use `WindowInsets`/`imePadding()` around the bottom composer so it stays above the keyboard. ([Navigation 3](https://developer.android.com/guide/navigation/navigation-3), [predictive back](https://developer.android.com/guide/navigation/navigation-event/handle-back), [adaptive list/detail back](https://developer.android.com/develop/adaptive-apps/guides/canonical-layouts), [edge-to-edge Compose setup](https://developer.android.com/develop/ui/compose/system/setup-e2e), [insets](https://developer.android.com/develop/ui/compose/system/insets-ui))

Use `currentWindowAdaptiveInfo()` or window size classes to switch between compact navigation and a wider list/detail arrangement; observe fold features/posture before spanning content across a hinge. For reduced motion, check `ValueAnimator.areAnimatorsEnabled()` (API 26+) and suppress nonessential app animations when the system has disabled animators; `Settings.Global.ANIMATOR_DURATION_SCALE` and `TRANSITION_ANIMATION_SCALE` are system settings, not app preferences to write. Give interactive Compose elements meaningful role, label, state, and custom actions so TalkBack does not depend on long-press alone. ([window size classes](https://developer.android.com/develop/adaptive-apps/guides/use-window-size-classes), [foldables](https://developer.android.com/develop/adaptive-apps/guides/foldables/make-your-app-fold-aware), [ValueAnimator](https://developer.android.com/reference/android/animation/ValueAnimator), [Settings.Global](https://developer.android.com/reference/android/provider/Settings.Global), [Compose semantics](https://developer.android.com/develop/ui/compose/accessibility/semantics))

## Widgets and the Galaxy Z Flip's cover screen

Three Glance widgets (`androidApp/.../Widgets.kt`, the iPhone's `ios/Widgets` mirror them): **Today's Tasks** for the home screen, each task a whole line across the widget's width with no rail; and the Timeline in two for the Flip's cover screen, on its rail as the app draws it, in a `LazyColumn` that scrolls: **Today's Tasks and Upcoming Meetings** (`AheadWidget`, with + for Quick Add) and **Activity** (`ActivityWidget`, no +), each line its marker and the task or node itself, each task once at the latest thing that happened to it (`Glimpse.activity`, `Row.asTask`, `GlimpseTest`). A widget cannot run the engine, so the app keeps a `Glimpse` after every read and every tick (`Engine.glimpse`): the rows as shown, sensitive ones without their words. A row opens its node in the app (`zoom`), + opens Quick Add, and a task's box opens the app with `tick`, which ticks the task and writes it to Tana at once (`MainActivity`, `Engine.tick`); Glance's lambda actions cannot start an activity on Android 12 and later, so opening uses `actionStartActivity`. ([Glance interaction](https://developer.android.com/develop/ui/compose/glance/user-interaction), [Glance lists](https://developer.android.com/develop/ui/compose/glance/build-ui), [updating a widget](https://developer.android.com/develop/ui/compose/glance/glance-app-widget))

The widgets have no background of their own, as the iPhone's on a clear Home Screen (foeken's screenshot on #718): the wallpaper shows through a light black veil (30 %) that keeps white words legible on a bright one, since RemoteViews cannot blur what is behind them as iOS's glass does, and everything is drawn in white at the iPhone's three strengths (primary, secondary, tertiary), in light and dark alike (`Glass` in `Widgets.kt`). As there, nothing is laid behind a marker to hide the rail, so the line stops short of each marker; a task's box is an outline (`drawable/box`), a check in it once done, dashed for an Inbox task (`drawable/inbox_box`); finished work's marker is a check in a ring (`drawable/ring`). The shapes say `<solid android:color="@android:color/transparent" />`: without it a tinted shape came out filled.

The Timeline's two widgets carry Samsung's Flex Window metadata beside Android's: `com.samsung.android.appwidget.provider` pointing at `<samsung-appwidget-provider display="sub_screen" />`, with `minWidth` 352dp, `minHeight` 339dp and `widgetCategory="keyguard"`, as Samsung asks; it is added in Settings, Cover screen, Widgets. The Flip5 measured here (SM-F731B, One UI on Android 16) reports its cover display as id 1, 748 × 720 px at 340 dpi, which is that 352 × 339 dp. An emulator has no cover screen, so the debug build also offers both on the home screen (`src/debug/res/xml/ahead_widget.xml`, `activity_widget.xml`), where `WidgetJourneyTest` pins them with `requestPinGlanceAppWidget` and drives it with UI Automator. ([Samsung Flex Window guide](https://developer.samsung.com/galaxy-z/flex_window.html), [Samsung widget codelab](https://developer.samsung.com/codelab/galaxy-z/widget-flex-window.html), [pinning a Glance widget](https://developer.android.com/develop/ui/compose/glance/pin-in-app))
