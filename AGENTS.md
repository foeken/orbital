# AGENTS.md — guide for future agents

This repo is **Orbital** (formerly Tana Companion): a macOS Electron outliner over the *new* Tana (home.tana.inc), synced live through Tana's own (undocumented, v1alpha1) platform protocol. Read this file first, then the docs it points to. Keep changes small and plain (CommonJS, no bundler, no framework, no new dependencies unless a few lines cannot do it).

Adding something — an IPC call, a `main/` module, a view or an app page, a Cmd+K row or built-in key, a renderer file, a setting — follows fixed steps across fixed files: [docs/EXTENDING.md](docs/EXTENDING.md) lists them, with the checks to extend.

## How Tana works (the short version)

- Everything is a **Loro CRDT document** with a `data` map (title, type, stateType, assignedToUris, participants, …) and a `content` map in loro-prosemirror layout (`{ nodeName, attributes, children }`, text as LoroText, mentions as inline maps). Task states: `proposed | open | closed | not_now` (Inbox / In Progress / Completed / Later). Ids are `tana:<kind>:<26-char lowercase ULID>`; kinds seen: text, event, space, user-profile, type, chat, canvas, agent, skill, collection, pin-map, org, image, call, transcript, screen-share, guest-profile, **search**. Tana's own client (`shared-*.js`) keeps two groups apart: document kinds (space, text, skill, transcript, chat, asset, image, audio, video, call, canvas, calendar-subscription, event, screen-share, artifact, agent, mcp-integration, collection, contact, search, action, widget-source, widget, suggestion-log, plus the schema kinds type and workflow; `Eie`/`Die`/`Oie` in the bundle of 2026-09-22) and system kinds (user-profile, guest-profile, org, pin-map, liveQuery, presence, user-inbox). A **saved search** (`tana:search:`) is a document holding a stored search definition that "runs exactly as stored"; types carry `searches: [{ uri, title, label, description }]` pointing at them, and they can be pinned to the sidebar. `liveQuery` is a *different* thing — a materialised query cache (`data.type: 'liveQuery'`, `queryType: 'nodes' | 'edges'`, `query`, `queryVersion`, `state: pending | ready | error`, `result`) — not a saved search.
- **Sync**: Connect-RPC at `https://home.tana.inc/platform`, service `tana.sync.v1alpha1.SyncService`: one `ServerSync` server stream per client (peer info, heartbeats every 15 s, live_document_update, resync_required) plus unary `ServerSyncCommand` (begin_document_sync → bootstrap → live_document_update, unsubscribe, document_action soft_delete). Creating a document = subscribing an unknown id with local ops (MISSING → push full snapshot). Details and the exact state machine: `docs/PLATFORM-PROTOCOL.md`.
- **Discovery/search**: `tana.graph.v1alpha1.GraphService.ListNodes` (nodeTypes, assignedTo, stateTypes, entityTypes, ownerIds, textQuery, event time window, sort). Owner chain (`GetOwnerChain`) gives a document's location (space/event); no owners = "Library". Type titles come from `nodeTypes: ['type']` nodes; members from `nodeTypes: ['user-profile']`. Inbox, Library and Types are one screen with three preset filters over one such query, and the pages that listed a single kind are saved searches (`docs/VIEWS.md`); each caches its own rows, so the row cache holds one row per (view, document).
- **Pins**: sidebar pins are a LoroTree in a private `tana:collection:` doc referenced by the user profile; date pins are in a `tana:pin-map:` doc; all written as normal live updates (`docs/PINNING.md`).
- **Auth**: the platform rejects MCP OAuth tokens (audience mismatch). The web session token from `/api/auth/session` works for everything. Tokens live 5 minutes; refresh with `?refresh=true`.
- **Not supported by Tana**: SVG/emoji icons on nodes (only `appearance.imageUri`/`hue`); the app no longer keeps icons of its own either. Event documents have empty content; meeting notes live in linked documents.
- **Chats** have no `content` outline either: the conversation is a LoroList at `data.messages` on the chat document, text is plain markdown in one LoroText with no marks, and mentions are `[label](tana:…)` links, so a chip needs no lookup. "Thought for N seconds" is `completedAt - sentAt` computed client-side, and "X accepted 1 change" is a human status-update message whose `attachmentUris` are the changed documents. Read only `data.messages`: a whole chat bootstraps to megabytes because tool output and the rendered system prompt are stored inline. `listNodes({ nodeTypes: ['chat'] })` returns only chats with no owner unless the request sets `includeOwnedChats: true`, and then every owned one (live 2026-09-23: 48 without, 417 with, nine in ten of the owned ones Tana's own background work). Every list that includes chats adds the owned `meeting` chats with a second query and leaves the other owned ones out, as Tana's own chat search does (`main/views.js` `listFilter`, issue #39). Details in `docs/CHATS.md`.

## Every platform

Orbital is the desktop app, the iPhone app (`ios/`), the Android app (`android/`) and the manual (`manual/`). A
change does not have to land everywhere, but it is never left out of one by forgetting: each PR's description says
under **Platforms**, one line each, "updated" or why it did not need to (`.github/pull_request_template.md`). The
Platforms workflow holds those lines to the diff (`scripts/platform-check.js`; `node scripts/platform-check.js
--body-file pr.md` before pushing): it fails on a missing line, an answer the diff contradicts, or "not needed" with
no reason, and notes where something usually follows.

- **The iPhone and Android mirror each other.** A change to one is made to the other in the same PR, with the same
  names and structure (each Kotlin screen names its Swift file on its first line), unless it is about something only
  one platform has, and the line says what.
- **The phones follow the desktop features they carry.** When the Timeline, chats and Ask Tana, Quick Add, Assigned to
  and Visible to, sensitive marks, demo mode, settings and the AI models, Auto-translate or pins change on the desktop,
  the phones change with them, or the line says why not (`MIRRORED` in the script lists them).
- **A new desktop feature does not come to the phones by itself.** The phone lines say "not needed: new desktop
  feature" unless the phones were asked for.
- **What both phones run changes both at once:** `ios/engine`, and the SDK and the desktop modules it bundles
  (`sdk/`, `main/timeline.js`, `main/settings.js`, `renderer/segments.js`). Check both phones.
- **The manual** follows anything a user can see or do on the desktop (updated when its PR leaves draft, above).

## Working rules that saved us time

- Verify against Tana read-only first: `node scripts/platform-cli.js …` (**not** `./node_modules/.bin/electron …`). Electron's GUI process aborts inside AppKit's `_RegisterApplication` whenever it starts under the agent sandbox, because LaunchServices is unreachable there, and every such run left a macOS crash dialog behind; the CLI now re-execs Electron itself and refuses with exit 3 when `CODEX_SANDBOX` is set, so real data needs an escalated (unsandboxed) run. `npm start` and the packaged app are GUI Electron too and need the same escalation. Details and measurements: `docs/ELECTRON-SANDBOX.md`. Only write to the user's real data when the user asked for it, and prefer scratch documents (`create` + `delete`) or the user's own test items ("Test Pin").
- **`Error: not authenticated` is not a sandbox or network failure**: it means this machine has no Tana session. The cookie partition lives in the shared userData (`~/Library/Application Support/Orbital/Partitions/tana`, named by `userdata.js`, which also moves an older `tana-tasks` folder there on the first start), not in the checkout, so one `npm run tana -- login` — a GUI window, escalated, the user signing in — serves every checkout and every worktree, and nothing in a worktree can stand in for it. Check with `node scripts/platform-cli.js whoami` before concluding anything about the platform.

- Renderer gotchas: `window.api` from contextBridge is a non-configurable global, so never declare a top-level `const api` in the renderer (use `tana`, declared in `renderer/state.js`); CSP is `default-src 'self'`, no inline scripts/styles; `renderer/mock.js` is used when `window.api` is undefined so the UI can be tested without the main process. - **`grep` here is ugrep, and it lies on big files.** On a multi-MB or very-long-line file (a downloaded Tana bundle, `sdk/proto/descriptors.js`, `icons.js`) it reports *no match* — exit 1, no error on stderr, so `|| echo ...` fallbacks read as "nothing found" rather than "the search never ran". It produced three false negatives in one session: "no `tana:search` in the bundle", "zero `\"search\"` strings" and "neither svg is referenced by build-icons.js", each wrong and each nearly reported as a finding. ## Integration checks and newer contracts

- `npm run check` includes SDK/database checks plus renderer auth/behavior checks. Also test ordinary edit notifications in a mock Electron window; helper-only tests once incorrectly treated all changed ids as deletions.
- `onChanged(docId, { meta })` is one document's change: the renderer patches that row from `doc:info` and keeps its cached metadata unless `meta` is true (main compares assignees, restriction, participants and type); `fields` true says a field's value moved, which re-reads the page's fields and keeps that metadata. `{ meta: false, own: true }` goes only to the page that typed the change (`setTitle`/`setText`/`setCell` called with `own`, main.js `typed`, main/state.js `sendChanged`): it already shows the words, so it patches the row copies and skips re-reading the page and the forced render; every other page, another pane of the same window included, gets the plain change. `onChanged(null)` is a global/pin refresh: the refresh writes every open view's rows into the cache before sending it, so the renderer reloads roots and runs no second query. `onRemoved(id)` is an explicit deletion. Unpin is not deletion. `onReleased(ids)` says main no longer keeps those documents live (the refresh sweeps): no change to them arrives any more, so the renderer forgets the outlines it keeps for them and reads them again when next drawn (renderer/app.js `forgetReleased`).
- The view refresh is pushed, not polled: every open view — one per window or split half (`openViews` in main/views.js) — has a live query (sdk/livequery.js, `watchViews`) whose answers schedule the refresh; a timer in main.js is only a 5-minute backstop, and a window gaining focus refreshes unless the last refresh finished within `FOCUS_FRESH_MS`. Two other live queries do their own work instead of waking the refresh: `watchMine` (the tasks you made for others) re-reads the watch set through `refreshWatched`, and `watchInbox` announces new Inbox tasks and updates the badge; an open saved search or type page has one from `watchRelated` (main/related.js) that re-reads that page. A refresh reads every open view and subscribes the first `LIVE_ROWS` (100) rows of each; its sweep unsubscribes what no open view, watch, undo step, pending read or page on screen still holds. A document read on demand (doc:info, a zoom, a mutation) is subscribed too, capped at the same number and let go oldest first (main/documents.js `onDemand`), and a read still waiting on a bootstrap holds its document (main/state.js `reading`) so no sweep drops it. Details: docs/VIEWS.md §4.
- Renderer rendering rules: `render()` is synchronous for user actions that need the DOM right after; anything that arrives on its own (metadata, pins, the rail, live updates, members) calls `renderSoon()`, which coalesces into one render per frame, and a metadata answer patches its own rows (`patchMeta`) instead of rendering. List rows are reused when `rowSig` is unchanged, so whatever a row is built from must be in that signature. Icons come from `iconNode` (a cloned template), not `innerHTML`.
- Preserve `Node.editable === false` in renderer: member profiles and known read-only nodes cannot enter editors. Backend mutation handlers enforce the same restriction.
- A built-in key is a palette row with an entry in `DEFAULT_HOTKEYS` (renderer/state.js): the document keydown handler finds the row by combo (`hotkeyFor`/`hotkeyIds`) and runs it through `runAction`, so it shows up in Cmd+K with its chip and can be re-recorded with Cmd+Shift+K. Only ⌘K, ⇧⌘K, the text-size keys, ⇧⌘⌫ and ⇧⌘↑/↓ are hard-coded (and listed in `RESERVED`). A key the outline handler answers to itself must compare against `hotkeyFor(id)` and preventDefault, which is what stops the document handler from running the row a second time.
- `sdk/access.js` implements the verified sharing/move subset. Do not extend ACL or move semantics by guessing CRDT keys or assuming ownership grants access.
- An event node proves *invited* and *scheduled* only. Attendance lives on its `tana:call:` document (same ULID, `data.ownerUri` back to the event): the `sessions` root holds one entry per live session and empties when the last participant leaves, `data.sessionLog` keeps the join/leave history. `sdk/calls.js` reads it (`currentCalls` answers "which meeting am I in right now"), `scripts/platform-cli.js incall` runs it live. Nothing in the graph says whether a participant is speaking or idle.
- A new request is a GitHub issue (open one first when it arrives in chat); a repeated request is a comment on its issue. The PR says `Closes #n` (or `Refs #n` when part of it stays open) and its description carries the verification evidence: what changed, how it was checked, what is left open, and what the manual gained. Orchestrator owns statuses; worker completion alone is not integrated verification. Write issue and PR bodies to a file and pass `--body-file`: they are full of backticks, which a double-quoted shell string runs as command substitutions.
